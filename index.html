Swift code quality guide

Force unwrapping (!)
Using ! to force-unwrap an optional crashes if the value is nil. Every ! is a time bomb. Replace with: guard let or if let for optional binding. ?? for providing a default value. guard let self inside closures. The only acceptable uses of !: IBOutlets (Xcode-generated, always set before use), known-safe cases with a clear comment explaining why the value cannot be nil. SwiftLint's force_unwrapping rule flags all ! uses.

Retain cycles in closures — the #1 Swift memory leak
When a closure captures self strongly and self holds a reference to the closure, neither can be deallocated. Fix: add [weak self] to the closure capture list: DispatchQueue.main.async { [weak self] in self?.updateUI() }. Use [weak self] for escaping closures (async callbacks, completion handlers, NotificationCenter observers). Use [unowned self] only when self is guaranteed to outlive the closure — crash if wrong. The Xcode Analyze tool (Product → Analyze) detects many retain cycles automatically.

A retain cycle occurs when two objects hold strong references to each other — neither can be deallocated. Most common: a closure captures self strongly and self holds the closure. Fix with [weak self] in the capture list: networkCall { [weak self] result in self?.handle(result) }. Detection: run Xcode Instruments (Leaks template), use Xcode Analyze, or check this tool for missing [weak self] patterns. Delegates should also be weak var delegate to avoid retain cycles between parent and child.
Force unwrapping is acceptable in limited cases: (1) IBOutlets — Xcode-generated, guaranteed set before use. (2) Testing code — crashes reveal bugs immediately. (3) Truly impossible nil — with a clear comment explaining why. Always prefer: guard let for required values, if let for optional handling, ?? for defaults. The SwiftLint force_unwrapping rule flags all !. Consider enabling it as a warning to gradually eliminate force unwraps from a codebase.
